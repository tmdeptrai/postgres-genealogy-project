        \section*{Abstract}
        This project builds a database to organize and study marriage records from France. We take 5,000 marriage documents and create a PostgreSQL database to store them in an organized way. The goal is to design the database so that it is well-organized, easy to use, and can answer questions about families and dates. This report explains how we organized the data and built the database system.

    \section{Introduction}

    Old documents and records from France contain important information about families and history. Many of these documents are stored in archives. To study and understand this information, we need to organize it in a database. This project focuses on creating a database system for marriage records from the Vendée region. We show how to take messy information and organize it in a clean, useful way.

    \subsection{Dataset Overview}

    We use a file called \texttt{mariages\_L3\_5k.csv} which contains 5,000 marriage records. Each record includes information about two people who got married, their parents, and the place and date of marriage.

    The data has these main parts:

    \begin{itemize}
        \item \textbf{Record Information:} Each record has an ID number and a date
        \item \textbf{Person A Information:} Name of the first person, and names of their mother and father
        \item \textbf{Person B Information:} Name of the second person, and names of their mother and father
        \item \textbf{Location Information:} The city (commune) and region (department) where the marriage happened
    \end{itemize}

    \subsection{Why This Project Is Important}

    When we have many old documents, it is difficult to find information or see patterns. A database makes this easier. Our database has these goals:

    \begin{enumerate}
        \item \textbf{Organization:} Store all the information in one place in a clear way
        \item \textbf{No Duplicates:} Each person should appear only once in the database, even if they appear in many records
        \item \textbf{Correct Information:} Make sure that all relationships between people and places are correct
    \end{enumerate}

    \subsection{Normalization Process}
    % TODO Explain how you transition the initial concepts into a normalized relational schema

    \begin{enumerate}
        \item \textbf{For 1NF:}\newline
              All values are atomic (each cell contains one piece of data).

              Each record is uniquely identified by an Act ID
              => Result: 1NF achieved

        \item \textbf{For 2NF:} \newline
              \textbf{Problem}: Repetition of data for parents, towns, and departments leads to redundancy.

              \textbf{Solution}: Separate entities so that every non-key attribute depends on the whole primary key

              \textbf{Resulting FDs}:
              \begin{verbatim}- Act_ID → (Type, Date, View_Num, Commune_ID, Person_A_ID, Person_B_ID)
- Person_ID → (Last_Name, First_Name, Father_ID, Mother_ID)
- Commune_ID → (Name, Dept_Code)
            \end{verbatim}
              => Result: 2NF achieved

        \item \textbf{For 3NF:} \newline
              \textbf{Problem}:
              \begin{itemize}
                  \item Transitive Dependency: The Department depended on the Town, which depended on the Act.
                  \item Parental names depended on the person
              \end{itemize}
              \textbf{Solution}:
              \begin{itemize}
                  \item Extracted Department into a standalone table to enforce valid codes (44, 49, 79, 85).
                  \item Established foreign keys \verb|(father_id, mother_id)| within the Person table to handle lineage without repeating names.
              \end{itemize}
              \textbf{Final FDs}:
              \begin{verbatim}Act_ID → (Act_Type, Date, View_Num, Commune_ID, Person_A_ID, Person_B_ID)
Person_ID → (Last_Name, First_Name, Father_ID, Mother_ID)
Commune_ID → (Commune_Name, Dept_Code)
Dept_Code → (Valid_Codes: 44, 49, 79, 85)
            \end{verbatim}
              => Result: 3NF achieved
    \end{enumerate}

    \subsection{Extraction}
    First, we pull all the data from the \texttt{mariages\_L3\_5k.csv} file. We used the pandas library in Python to help with this. An important step was to read everything as text first, so we didn't accidentally change data, like dropping the '0' from a department code like '05'. We also made sure to use UTF-8 encoding, which helps read special French characters correctly.

    \subsection{Transformation}
    This is where we do most of the cleanup work. Our script goes through the raw data row by row and gets it ready for our normalized tables.

    \subsubsection{Data Cleaning}
    We made a simple cleaning function that does two things:
    \begin{itemize}
        \item It removes any extra spaces from the beginning or end of each piece of data.
        \item It finds any empty or "n/a" values and marks them as properly missing, so we can handle them consistently.
    \end{itemize}

    \subsubsection{Finding and Removing Duplicates}
    To avoid storing the same person or town multiple times, our script keeps track of what it has already seen.
    \begin{itemize}
        \item \textbf{Departments and Towns:} It checks for valid department codes and skips any rows with bad data. It makes sure a town is unique by looking at both its name and its department code.
        \item \textbf{People:} To decide if a person is unique, we look at their full name and also who their parents are. This helps tell apart two people who might have the same name.
    \end{itemize}

    \subsubsection{Fixing Formats}
    We also had to fix a few things to match our database design:
    \begin{itemize}
        \item \textbf{Dates:} We converted the date from the "DD/MM/YYYY" text format into a real date that the database can understand.
        \item \textbf{View Number:} We took columns like "48/210" and just kept the first number (48), which is the page number we care about.
    \end{itemize}

    \subsection{Loading}
    Instead of manually importing the files, we used a second Python script, \texttt{main.py}, to automatically load our cleaned data into the PostgreSQL database. This script uses a library called SQLAlchemy, which helps Python talk to databases.

    The loading process is done carefully to avoid errors:
    \begin{enumerate}
        \item \textbf{Final Check:} Before loading, the script does one last check on our cleaned data tables to make sure all the ID numbers are valid integers and that no essential information is missing.
        \item \textbf{Order of Operations:} It loads the tables in the correct order: first \texttt{department}, then \texttt{town} (which needs departments to exist), then \texttt{person}, and finally \texttt{act} (which needs towns and people).
        \item \textbf{Handling People:} The \texttt{person} table was a bit tricky because a person's parents are also in the same table. To solve this, we first insert all people with their parent fields empty. Then, once everyone is in the table, we go back and add the parent-child links.
        \item \textbf{Batching:} To make it faster, the script inserts the data in large chunks (batches) instead of one row at a time.
        \item \textbf{Updating Sequences:} After inserting everything with specific IDs, we reset the database's automatic ID counters. This ensures that if we add new data later, we won't have any ID conflicts.
    \end{enumerate}

    \section{Bonus: Scalability \& Noisy Data}

    In this section, we test our database design and ETL pipeline against a much larger and more realistic dataset: a file named \texttt{mariages.csv} containing approximately 564,000 records. This file, unlike the initial 5k dataset, contains more noisy and inconsistent data.

    \subsection{Challenge Overview}
    The primary goals were:
    \begin{enumerate}
        \item To successfully process and load the 564k records without changing our database schema.
        \item To identify and handle the data quality issues ("noise") found in the larger file.
        \item To run the same five genealogical queries and compare the results with those from the initial 5k dataset.
    \end{enumerate}

    \subsection{Difficulties Encountered and Solutions}
    Running our initial script on the new dataset immediately revealed several issues. Here’s a summary of the problems we found and how we solved them.

    \subsubsection{Problem 1: Performance with Large Data}
    \textbf{Issue:} Reading all 564,000 rows into a pandas DataFrame at once was very slow and used a lot of memory.

    \textbf{Solution:} We modified our script to read the CSV in smaller chunks. This meant the program processed the file piece by piece instead of all at once, which significantly improved performance and reduced memory usage.

    \subsubsection{Problem 2: Inconsistent Date Formats}
    \textbf{Issue:} The script failed on many rows because the dates were not in the expected \texttt{DD/MM/YYYY} format. We found formats that contained only the year of the event like \texttt{\'00/00/1731\'}, or were missing specific day or month information like \texttt{\'00/07/1691\'}. These incomplete dates could not be directly parsed.

    \begin{figure}[H]
        \centering
        \includegraphics[width=0.7\textwidth]{../figures/problem2-inconsistent-date.png}
        \caption{Inconsistent Date Formats}
        \label{fig:problem2-date-formatting}
    \end{figure}

    \textbf{Solution:} We improved our date-parsing logic to be more flexible. We used a date-parsing library that can intelligently guess common date formats and added more robust \texttt{try-except} blocks to handle and log the formats we couldn\'t automatically convert, rather than crashing the script. For incomplete dates, we decided to store them as `NULL` in the database to preserve the record while acknowledging the missing information.

    \subsubsection{Problem 3: Missing Department Codes}
    \textbf{Issue:} Many rows in the larger dataset had empty or unspecified department codes in the source data. After our initial cleaning, these appeared as \texttt{\'None\'} (e.g., \texttt{Row 5755: unknown dept\_code None — skipped}). Our database schema requires a \texttt{town} to be linked to a \texttt{department}, so records without a department code could not be processed.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\textwidth]{../figures/problem3-NoneDept.png}
        \caption{Empty Department Code}
        \label{fig:problem3-none-dept-code}
        \end{figure}

    \textbf{Solution:} We chose to filter out and log any records where the \texttt{dept\_code} was missing (i.e., \texttt{\'None\'}). This ensures that all data loaded into our \texttt{town} table correctly references an existing \texttt{department}, maintaining data integrity in accordance with our schema.

    \section{Conclusion}

This project successfully met the goal of designing and implementing a relational database for French genealogical records. Starting from a single, flat CSV file, we designed a normalized schema in Third Normal Form (3NF) to ensure data integrity and minimize redundancy. Our final design consisted of four interconnected tables: \texttt{department}, \texttt{town}, \texttt{person}, and \texttt{act}.

A key part of our work was developing a robust ETL (Extract, Transform, Load) pipeline using Python. This pipeline not only cleaned and validated the initial 5,000 records but was also designed to be scalable. As demonstrated in the bonus section, our system is capable of handling a much larger, "noisy" dataset of over 500,000 records with only minor adjustments to handle performance and data inconsistencies.

We proved the effectiveness of our database by running a series of genealogical queries, successfully extracting meaningful information such as marriage statistics and location-based data. Overall, this project provided practical experience in database modeling, data normalization, and building an automated pipeline to handle real-world data challenges.
